# Regenerating this grammar's generated data

Two things in this repository are generated and never hand-edited:

| | generated by | workflow |
|---|---|---|
| `src/builtins.h` | `tools/generate_builtins.py`, from a live 4D release | `update-builtins.yml` |
| `src/parser.c`, `src/grammar.json`, `src/node-types.json` | `tree-sitter generate`, from `grammar.js` | `regenerate-parser.yml` |

Both are load-bearing, and both fail quietly rather than loudly if they go
stale, which is why each has a workflow that regenerates it and verifies the
result before proposing a change.

---

# builtins.h

`src/builtins.h` holds the 4D command names from `Command name()` plus the
constant names from `4D_ConstantsEN.xlf`.

It is not decorative. `src/scanner.c` includes it and the lookup is a **binary
search**, so the table's ordering is a correctness property: an unsorted table
does not fail, it just stops finding names. The table committed today leaves
**401 of its 3944 rows unreachable** -- `ABORT PROCESS BY ID` after `ABORT`,
the whole `_o_…` family out of order -- so multi-word builtins never matched in
the scanner. The first run of `update-builtins` is expected to produce a large
diff that is mostly reordering; that is the fix.

## The two halves

| | owns | lives in |
|---|---|---|
| **4D** | which names exist | `tools/Builtins/Project/Sources/Methods/generate_builtins_dump.4dm` |
| **Python** | how they are written | `tools/generate_builtins.py` |

The 4D side only enumerates and writes JSON. It never decides order, escaping
or `#define` values, so a change in presentation can never masquerade as a
change in the 4D language.

`generate_builtins.py` refuses to guess. A duplicate name, a command and
constant sharing a name, a name that would not fit the scanner buffer, or a dump
smaller than the table it replaces are all hard errors: each one means 4D
produced something unexpected, and a silent fix would hide it.

## Running it

Automatic, which is the normal path: run the **Update builtins.h** workflow with
a version such as `21 R5` or `21.2`, or leave it empty for the newest published
release. It opens a pull request only when the table changed. A weekly schedule
runs the empty form.

**Nothing needs rebuilding afterwards.** The parser sources compile `builtins.h`
directly, so a merged table takes effect the next time `src/parser.c` and
`src/scanner.c` are compiled. Anyone who embeds this grammar pins a `rev` --
`miyako/language-4dm-zed` does, in its `extension.toml` -- and has an
**Update grammar revision** workflow there that moves the pin and rebuilds.

Manual, if you want to see the data first:

```bash
# Windows layout: the archive unpacks to tool4d/tool4d.exe
tool4d --project tools/Builtins/Project/Builtins.4DProject \
       --startup-method generate_builtins_dump \
       --user-param '{"dump":"/tmp/builtins.json","xlf":"/Applications/tool4d/tool4d/21R4/tool4d.app/Contents/Resources/en.lproj/4D_ConstantsEN.xlf"}' --dataless

python3 tools/generate_builtins.py --dump /tmp/builtins.json --header src/builtins.h          # preview
python3 tools/generate_builtins.py --dump /tmp/builtins.json --header src/builtins.h --write  # apply
python3 tools/generate_builtins.py --dump /tmp/builtins.json --header src/builtins.h --check  # exit 3 if stale
```

`--build` stamps the build number (`21R4.100186`); the workflow passes the one
`tool4d --version` reports, which also catches a download that quietly resolved
to another build. The stamp lands in a `// Source release:` comment, so the
header always says which release it describes.

## Checking the table

    python3 tools/check_builtins.py src/builtins.h

Exits 0 when every row is ordered by `fourd_stricmp` and findable by the binary
search, and when the two computed `#define`s match the data. It re-reads the
header from disk and re-implements the comparison, so it is independent of the
script that wrote it, and needs no toolchain -- which is how a Windows runner
can gate on it.

    cc -std=c11 -Wno-unused-function -Isrc -o /tmp/check tools/check_builtins.c
    /tmp/check

is the same check against the real inline functions in the header, for machines
that do have a C compiler; the workflow runs it when one is present, together
with `cc -fsyntax-only src/scanner.c`.

The workflow runs the gate after rendering, so a broken table can never reach a
pull request.

## Why the workflow runs on Windows

The three tool4d archives are not interchangeable. `tool4d_win.tar.xz` is
self-contained -- 27 MB with `Kernel.dll`, `xerces-c`, `icu` and `libssl`
bundled -- while `tool4d_linux.tar.xz` is a bare ELF binary whose `DT_NEEDED`
list expects the distribution to provide LLVM's C++ runtime: `libc++.so.1`,
`libc++abi.so.1` and `libunwind.so.1` (LLVM's libunwind, soname 1, not GNU's
soname 8). On a hosted Ubuntu image those are a trap: Ubuntu 26.04 registers
`libc++1-18` in its package lists with no files on disk, so `apt-get install`
answers "0 newly installed" and the loader still cannot start the binary. The
Windows build sidesteps the question, and 4D tests it first anyway.

No macOS archive could be found under any spelling (`mac`/`macos`/`osx`,
`.tar.xz`/`.zip`), so `resolve_version.py` offers `windows` and `linux` only.

## The pasteboard tools

`generate_command_list.4dm` and `generate_constant_list.4dm` are untouched and
still work as before: they put the lists on the clipboard for the regex grammar
helpers. They differ from the CI path on purpose -- they uppercase and strip
spaces, because `command_to_regex.4dm` wants normalized names, while
`builtins.h` stores `ARRAY INTEGER` and `Attribute published SQL` verbatim.

## Versions

4D publishes two trains, and a branch only pairs with its own train:

```
LTS        branch 21.x    version 21.2
R-release  branch 21 Rx   version 21 R5     (the space is URL-encoded)
```

There is no index to query -- a directory path answers 200 with an 87-byte HTML
stub -- so `resolve_version.py` treats only a real archive as evidence that a
version is published. Newer R-releases 404 until 4D publishes them; that is a
beta, not a wrong URL.

# The parser

`src/parser.c` (4 MB of C), `src/grammar.json` and `src/node-types.json` are
generated from `grammar.js` by the tree-sitter CLI. Nothing stops `grammar.js`
from being edited without them being regenerated, and when that happens the
parser every editor actually compiles is the old grammar while the file a reader
opens is the new one -- the queries, the fixtures and the code disagree and
nothing says so.

At the time of writing the two are genuinely out of sync: the committed
`src/grammar.json` holds **181 rules** while `grammar.js` defines **51**.

## Running it

    npx tree-sitter-cli@0.22.4 generate

The version is pinned. Generation is deterministic for a given CLI version, so
"no change" is a meaningful answer; letting it float would turn a dependency
bump into a whole-file rewrite that hides real grammar changes. `0.22.4` emits
`LANGUAGE_VERSION 14`, which is what is committed.

The **Regenerate parser** workflow runs on every push that touches `grammar.js`,
then:

1. regenerates, and keeps only the three artefacts above -- the CLI also
   migrates `package.json`, the bindings and `src/tree_sitter/*.h` to its own
   template, which is not this workflow's business;
2. compiles `src/parser.c` and `src/scanner.c` (`cc -fsyntax-only`);
3. parses `test/smoke.4dm` and fails if any `ERROR` or `MISSING` node appears;
4. opens or updates the `ci/regenerate-parser` pull request, quoting the
   `STATE_COUNT`, `SYMBOL_COUNT`, `TOKEN_COUNT` and rule-count changes.

It deliberately does not block pull requests. A stale tree is a fact to surface
with a diff, not a red cross on unrelated work.

`test/smoke.4dm` exists for step 3 and is worth a look before touching
`grammar.js`: it exercises the constructs that depend on the external scanner --
multi-word commands and constants, `_o_…` style constants -- plus `#DECLARE`,
`Case of`, `Begin SQL` and `Try`.

## Before merging a regeneration

Check the node names the highlighting queries use (`languages/4d/*.scm` in
`miyako/language-4dm-zed`) against the new `src/node-types.json`. A renamed rule
shows up there and nowhere else -- the grammar still generates and still parses.
